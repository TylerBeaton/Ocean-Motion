# Unity joint visual preview in Fusion

This is an offline visualization experiment with short-preview and full-CSV modes, not exact inverse kinematics or actuator control. It does not modify the Unity project.

On a disposable copy of the Fusion design, add the existing `UnityJointVisualPlayback.py` script to Fusion's Scripts and Add-Ins panel. It requires the adjacent `JointPoseProbe` and `UnityBoatTelemetryPlayback` script folders to remain in this project's `Tools/Fusion360` directory.

## Popping/drift investigation — next hands-on gate

The CSV controller measured only heave and two local tilts, then applied a fixed response matrix through six coupled joint writes. It neither controls lateral travel/yaw nor guarantees that its initial response remains accurate later in the motion. Per-joint `doEvents()` also exposed partially updated configurations. The playback path now pumps events once after all six commands and checks the joint excursion again after event processing. This removes the script's intermediate event boundaries, **not** Fusion's sequential constraint solves; it is not an atomic drive or a drift fix. Calibration/restoration still use the original probe's event handling. The recorded full run showed recognizable motion but the user reported sideways popping/drift; accurate full-sequence reproduction is not established.

Run the same script on a clean duplicate and enter **`pose-test`** instead of `full`. No CSV is requested. This applies one small target (world Z +1 mm; local X/Y rotation-vector components +0.15° each) with unchanged world X/Y and zero local Z rotation. It uses `root.transformOccurrences([top], [matrix], False)` rather than assigning `top.transform2` or driving six servos independently. The installed Fusion API documents `False` as honoring joints and moving the occurrence the best it can; success is **not** a promise of exact target placement.

The test now approaches the same small target in ten steps, with a viewport refresh and 0.3-second pause after each step. It reads back the entire top pose and all six revolute angles. It also measures the world transforms of both component occurrences attached to each revolute joint and their relative transform. Shared rigid-body movement cancels out of the relative measurement; this helps distinguish whole-assembly motion from actual servo-body articulation even when `rotationValue` stays unchanged. Zero measured relative rotation produces an explicit `NO SERVO-BODY ARTICULATION DETECTED` message rather than treating the top-pose match as linkage proof.

It reports whether full-pose error is within 0.1 mm / 0.05°, and retains the 35° visual joint excursion and 25 mm / 8° plate bounds, checked after each step. Before dismissing the result, inspect all six linkages and confirm the base stayed still. Copy the full result, including the per-joint body measurements. OK attempts restoration via the same joint-aware API; a pose or joint mismatch warns not to save. Preserve the original design and do not save this experimental duplicate. No locks, joint definitions, geometry, or hardware output are changed.

The earlier instantaneous test reported exactly the requested top pose but zero changes in all six revolute readbacks. The user observed a slight upward plate movement and a return after OK; linkage articulation and base stability were not established by that observation. The slowed, instrumented version still needs a Fusion run. Its local tests do not simulate Autodesk's constraint solver.

This is a single-pose feasibility gate, **not a replacement CSV controller yet**. Even a passing pose measurement needs visible linkage validation and a repeatable return to neutral before trying a short CSV segment with this API. Pure-Python tests cover event boundaries, coordinate construction, explicit joint honoring, readback, rejected/inaccurate poses, bounds, restoration on failure, and mode isolation. They cannot exercise Autodesk's constraint solver.

API reference: https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/Component_transformOccurrences.htm (also verified against the installed `adsk/fusion.py` wrapper).

## Hands-on result and reuse boundary

On a disposable Fusion duplicate, the user reported a complete ten-frame playback of `boat-telemetry-test-000-20261005-140749.csv` from 2.02 to 5.62 seconds, with all six linkages remaining connected. The final requested Fusion heave/X tilt/Y tilt was `(-8.73 mm, -4.09°, -4.05°)` and the reported achieved motion was `(-8.55 mm, -4.41°, -3.94°)`. The report also showed unrequested world X/Y displacement of `(-4.50 mm, +5.71 mm)` and local Z rotation of `+0.78°`. Calibration settled `0.37 mm, 0.09°` from the starting pose. No repeatability or physical-actuator validation has been established; playback on other captures or a different starting pose may drift or trip the bounds. A separate calm-to-bow capture passed but contains essentially no roll, so it is not evidence of three-axis playback.

Reusable output: a short, bounded CSV-to-assembly-joint visualization path with explicit axis mapping and target-versus-achieved reporting. The scales, joint cap, and resulting motion are for presentation, not an IK contract or hardware travel/servo limits. For public presentation label it: “Unity-recorded boat motion driving a Fusion assembly — scaled visual prototype; not hardware control.” Capture the Fusion viewport on a clean duplicate, then inspect and trim the screen recording rather than claiming real-time or exact-pose playback.
